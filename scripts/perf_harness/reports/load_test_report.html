2. Quota Analysis & System Bottlenecks

🚨 Primary Bottleneck: Cloud Firestore Document Reads (50,000 / day)

Each active student consumes ~99 document reads during an active session covering the dashboard, timetable, attendance history, study materials, CBT exam, results, fee ledger, and notices. The admin portal consumes an additional ~1,500 - 3,500 reads/day due to real-time streams over courses, batches, students, and fee_payments.

Calculated Capacity:
(50,000 daily read quota - 2,500 admin overhead) / 99 reads per student = 480 active student sessions/day. Accounting for student re-visits and real-time listener updates, the realistic daily student capacity is 250 to 320 daily active students (representing an enrolled base of ~450 to 550 students at typical 60% daily engagement).

🚨 Secondary Bottleneck: Firebase Realtime Database Simultaneous Connections (100 Max)

The CBT examination proctoring engine relies on Firebase Realtime Database (live_exams/{testId}/sessions/{studentUid}) for 3-second live heartbeats and admin monitoring. On the Firebase Spark plan, RTDB enforces a hard limit of 100 simultaneous connections.

Impact: If a scheduled exam has more than 100 students connecting simultaneously, any student beyond candidate #100 will encounter a connection rejection.

✔ Non-Bottlenecks (Zero Quota Risk under Free Tier):
  • Document Writes: Only ~2.1 writes per student session (CBT exam submit + payment verification proof). 1,000 daily students consume only ~2,100 writes/day against the 20,000 write allowance (10.5% of quota).
  • Database Storage: 1 GiB free storage is completely safe because all binary files (PDFs, banners, student fee payment screenshots) are stored on Cloudinary! Firestore only stores JSON documents (~5 KB per student), which easily accommodates >50,000 students.
  • Egress Network Bandwidth: Firestore provides 10 GiB/month outbound data. Average student session transfers ~50 KB, meaning 300 daily active students consume only ~15 MB/day (~450 MB/month, or 4.5% of quota).
  • Firebase Authentication: 50,000 Monthly Active Users (MAU) is free, which far exceeds the 500-student capacity.

4. Recommended Architectural Optimizations

1. Cache Batches & Courses Locally with SharedPreferences / Hive

In home_repository.dart (line 447), the student home screen listens to ALL 30 batches in Firestore on every page load: db.collection('batches').snapshots().
Fix: Batches and courses rarely change. Cache them locally for 24 hours. This immediately eliminates 30 Firestore reads per student session, expanding daily active student capacity from ~300 to ~450 students on the free tier!

2. Paginate Student Directory in Admin Portal

In admin_state_controller.dart (line 206), the admin web dashboard loads the entire students collection on initial load.
Fix: Implement Firestore query pagination (.limit(25).startAfterDocument(...)) so the admin loads only 25 students per page rather than all 500+ records.

3. Stagger CBT Exam Slots for Over 100 Students

To respect the 100 concurrent RTDB connection limit on Spark: Conduct exams in two or three time slots (e.g., Morning Batch: 9:00 AM, Afternoon Batch: 1:00 PM, Evening Batch: 5:00 PM). Each slot with 80-90 students will execute with zero errors on the free tier.

4. Increase RTDB Proctor Heartbeat Interval from 3s to 5s

In exam_screen_page.dart, the heartbeat timer fires every 3 seconds: Timer.periodic(const Duration(seconds: 3), ...). Changing this to 5 or 6 seconds cuts RTDB write throughput and egress transfer by 40% to 50% without noticeable impact on admin live monitoring.
